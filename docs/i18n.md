# Languages (i18n)

Zekra ships in 18 languages on every surface: the web console, mobile, desktop, the browser
extension, account emails, API messages and push notifications, plus the store listings.

| Code | Language | Code | Language | Code | Language |
| --- | --- | --- | --- | --- | --- |
| `en` | English | `it` | Italiano | `hi` | हिन्दी |
| `ar` | العربية (RTL) | `ru` | Русский | `id` | Bahasa Indonesia |
| `es` | Español | `tr` | Türkçe | `nl` | Nederlands |
| `fr` | Français | `zh-Hans` | 简体中文 | `pl` | Polski |
| `de` | Deutsch | `ja` | 日本語 | `vi` | Tiếng Việt |
| `pt-BR` | Português (Brasil) | `ko` | 한국어 | `uk` | Українська |

English and Arabic are written by the team. The other 16 languages are **machine-assisted**:
each catalog says so in its `"//"` key, and each one is waiting for a native-speaker review
(see [Reviewing a language](#reviewing-a-language)).

## How it fits together

### One locale table

`web/lib/intl/locales.ts` is the source of truth. It holds `LOCALES`, `LOCALE_INFO` (native
name, English name, `Intl` tag, script family), the negotiation helpers (`matchLocale`,
`localeFromAcceptLanguage`) and `dirForLocale()`. It is plain TypeScript, so web, desktop
(alias `@`) and mobile (alias `@shared`) all import the same file.

Direction is not stored per language. It comes from the language subtag (`RTL_LANGUAGES`:
ar, fa, he, ur…), so Arabic is RTL today and Persian or Hebrew would be RTL the day they are
added. Every surface sets direction through `dirForLocale()`; nothing compares against `"ar"`.

The Go servers keep their own copy of the list (`var Locales` in `internal/account/i18n.go` and
`plugins/brain/internal/brain/i18n.go`). `scripts/i18n/check.mjs` fails CI if the copies drift
apart.

### Messages

Messages are ICU MessageFormat: `{name}` placeholders, `{count, plural, one {…} other {…}}`
and `select`. `web/lib/intl/icu.ts` formats them, with plural rules from `Intl.PluralRules`
for the active language. That is why ru, uk, pl and ar can use `few` and `many`, and why
ja, zh and ko need only `other`. A missing key, or a message that fails to parse, falls back
to English, then to the key itself.

Dates, numbers and relative time always go through `Intl`, using the locale's `intl` tag. On
web, `useTranslations()` returns `{ t, locale, dir, isRtl, formatDate, formatNumber, timeAgo }`.
Lists ("footnotes and raw HTML blocks") use `Intl.ListFormat` rather than a hard-coded " and ".

### Per surface

| Surface | Catalogs | How the language is chosen |
| --- | --- | --- |
| Web console | `web/lang/<area>.<locale>.json`. en/ar are bundled; the server loads the others (`lang/index.ts`). | URL prefix (`/de/…`), then the `NEXT_LOCALE` cookie, then `Accept-Language`, then English (`web/proxy.ts`). Signed in, the profile language (`account_profiles.locale`) is applied and saved when you change it in the picker. |
| zekra.dev (marketing site) | en/ar only | Other languages fall back to English. Out of scope for now. |
| Mobile | `mobile/src/i18n/features/*.ts` (en, ar) + `mobile/src/i18n/locales/<locale>.json`; native iOS/Android strings in `mobile/locales/<locale>.json` | OS languages (`expo-localization`), unless a language is picked in Settings → Appearance (saved to the profile). RTL via `I18nManager`, which applies from the next launch. |
| Desktop | renderer `desktop/src/renderer/i18n/` + `locales/<locale>.json`; main process (menus, tray, updater, Services) `desktop/src/main/locales/<locale>.json` | Settings → General; until a language is picked, the OS languages (`app.getPreferredSystemLanguages`, matched by `matchSystemLocale`). On macOS the app also sets its `AppleLanguages` so native menus and the window follow, including RTL. electron-builder ships the 18 language packs. |
| Browser extension | `extension/_locales/<chrome code>/messages.json` (Chrome i18n; `pt_BR` and `zh_CN` are Chrome's names for pt-BR and zh-Hans) | The browser's UI language (`chrome.i18n`). `extension/i18n.js` localizes the popup and options pages (`data-i18n`) and sets `lang`/`dir` from each catalog's `langTag`/`langDir`. |
| Account emails and API messages | en/ar inline in Go; others in `internal/account/locales/<locale>.json` (embedded) | Request body `locale`, then the saved profile language, then `Accept-Language`, then English. Missing keys fall back to English one by one. |
| Push notifications | en/ar inline; others in `plugins/brain/internal/brain/locales/<locale>.json` | The language each device registered with, so one account can get German on the phone and English on the tablet. |

Some things are deliberately not translated:

- the `Source:` / `Tags:` lines that the extension writes into a note (they belong to the note's content);
- Mahaam SDK strings (en/ar, owned by Mahaam);
- the names in [lang/glossary.md](../lang/glossary.md) that never change: Zekra, MCP, OAuth, Markdown, product and tool names.

### Fonts

Latin, Cyrillic and Arabic use the Nasaq stacks: Inter, and IBM Plex Sans Arabic for Arabic.
Chinese, Japanese, Korean and Hindi switch to the platform's native faces (PingFang / Hiragino /
Apple SD Gothic / Noto Sans CJK / Noto Sans Devanagari / Microsoft YaHei / Yu Gothic / Malgun
Gothic / Nirmala UI), chosen by the `script` field in `LOCALE_INFO`. Those scripts also turn
off negative letter-spacing. No CJK webfont is downloaded.

## The CI gate

`node scripts/i18n/check.mjs` runs in CI (the `i18n` job in `.github/workflows/ci.yml`) and
fails on any of the following:

1. **Locale lists:** the web table, `scripts/i18n/catalogs.mjs` and the two Go tables disagree.
2. **Parity:** a language is missing a key that English has, or has a key English doesn't.
   This covers every catalog of every surface.
3. **Messages:** an ICU message fails to parse; a placeholder, plural/select variable or
   `<tag>` doesn't match English; a plural has no `other`; or an extension `$1`…`$9` doesn't
   match.
4. **Store listings:** a field in `store/asc` or `store/play` is over the store's character
   limit, or a `store/web/<locale>.md` is missing.
5. **Hard-coded UI strings:** literal JSX text, or a literal `placeholder` / `title` /
   `aria-label` / `alt` / `label` of two or more words, in `web/app`, `web/components`,
   `mobile/app`, `mobile/src/{components,screens}` or `desktop/src/renderer`. Counts are
   compared per file with `scripts/i18n/hardcoded-baseline.json`, and a file's count may only
   go down. Today two files remain, both intentional: vendored shadcn sidebar copy (desktop)
   and the "BY FADY MONDY" site credit. After removing strings, run
   `node scripts/i18n/check.mjs --update-baseline`.

The placeholder and ICU checks are unit-tested in `web/lib/intl/icu.test.ts`. The Go fallback
and the locale resolution order are tested in `internal/account/i18n_test.go` and the brain's
`i18n_test.go` / `devices_test.go`; the desktop OS-language match in `desktop/test/locales.test.cjs`.

## Adding or changing copy

1. Add the English string to the surface's English catalog, and the Arabic one next to it.
2. Run `node scripts/i18n/export.mjs`. It writes every English catalog, flattened, to
   `.i18n-work/source/` (git-ignored).
3. Translate the new keys into `.i18n-work/out/<locale>/` (same file layout), following
   [lang/glossary.md](../lang/glossary.md).
4. Run `node scripts/i18n/validate-work.mjs <locale>` to check each language's work files
   before merging.
5. Run `node scripts/i18n/merge.mjs`. It writes the catalogs back in each surface's own format
   (Chrome `messages.json` for the extension) and adds the machine-assisted note.
6. Run `node scripts/i18n/check.mjs`. It must report 0 problems.

Until step 5, the new keys simply show in English in the other 16 languages. Nothing breaks
in the meantime, but CI's parity check fails, which is what keeps a language from silently
falling behind.

### Adding a language

1. Add the language to `LOCALES` and `LOCALE_INFO` in `web/lib/intl/locales.ts`, to `LOCALES`
   in `scripts/i18n/catalogs.mjs` and to both Go `var Locales`. If Chrome names it
   differently, add it to `CHROME_LOCALE`.
2. Translate it (steps 2–6 above), add its glossary column, and add store listings in all
   three formats.
3. Desktop: add its language pack to `electronLanguages`. iOS: add it to
   `CFBundleLocalizations` via `mobile/app.json`.

## Reviewing a language

Each machine-assisted language needs one native-speaker pass:

1. Check the glossary row first (Brain / Memory / Recall / Vault). Changing a term there and
   re-running the translation is cheaper than fixing 3,600 strings by hand.
2. Read the catalogs in the running app instead of the JSON: the web console with `/<locale>/`,
   mobile and desktop with the OS language set.
3. Look at the tight spots: buttons, tab bars, stat cards (their labels truncate), table headers
   and push notification titles. German, Russian, Ukrainian and Polish run 30–60% longer than
   English. Layouts use `flex-wrap` / `min-w-0 truncate` rather than fixed widths. The one label
   long enough to truncate on a phone (`sources.statLastSync`) has a shorter form in ru, uk, pl,
   es, pt-BR and it.
4. When a language is reviewed, remove the machine-assisted note from its catalogs and its
   `MACHINE_ASSISTED` entry in `scripts/i18n/catalogs.mjs`.

## Search across languages

Recall is hybrid: BM25 for exact words, plus vector search. The two behave differently across
languages.

- **Embeddings:** `BAAI/bge-m3` (with the `bge-reranker-v2-m3` reranker), served by
  `plugins/brain-tei`. It is multilingual (100+ languages) and cross-lingual, so a question
  in German finds a memory written in Japanese. Nothing needed to change.
- **BM25 tokenizer:** production runs `BRAIN_BM25_TOKENIZER=zekra_ml`, pg_tokenizer's
  `llmlingua2` model (an XLM-RoBERTa SentencePiece vocabulary). It splits Chinese, Japanese,
  Korean and Devanagari into subwords, so CJK and Hindi text gets real BM25 terms instead of
  whole unsegmented runs. BM25 is lexical: it matches within a language, and the vector side
  covers matching across languages.
- **Self-hosting:** the default tokenizer (`zekra_bm25_tok`, see `infra/grant-bm25.sql`) is a
  fixed-vocabulary probe, not production-grade for any language. Self-hosters should
  provision `zekra_ml` as that file describes (`docs/self-hosting.md`).

**Follow-up (not done here, as it needs a database we're allowed to touch):** measure recall
on a dev brain with a small fixture set in zh, ja, ko and hi (same-language and
cross-language queries), and confirm that `llmlingua2` doesn't over-split Hindi conjuncts.
No production data was read or changed for this work.

## Store listings

These are files only. Nothing is uploaded from this repo.

- `store/asc/<asc locale>.json`: App Store Connect fields: `name` ≤ 30, `subtitle` ≤ 30,
  `keywords` ≤ 100, `promotionalText` ≤ 170, `description`, `whatsNew`.
- `store/play/<play locale>.json`: Google Play fields: `title` ≤ 30, `shortDescription` ≤ 80,
  `fullDescription` ≤ 4000.
- `store/web/<locale>.md`: the long-form listing for the website and other stores.

The English name is "Zekra: AI Second Brain"; the Arabic name is "ذكرى: عقلك الثاني". The
other languages keep "Zekra" and translate the descriptor. File names use each store's own
locale codes (for example `de-DE`, `zh-Hans` on the App Store and `zh-CN` on Google Play).
`check.mjs` enforces the limits.
